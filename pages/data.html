The data

Everything the map shows is one record, and the record is public. This page says what is in it, how to take it away, on what terms, and how to read it over the same interface the map reads it from.

What the record is

One file of comma-separated values, one camera per line, kept in the site's repository as data/cameras.csv. It is edited by hand, from the documents - the Metropolitan Police's published live facial recognition deployment records, the British Transport Police's deployment register, and named press reporting for the shops and the fixed cameras - and nothing in it is estimated. Where a source gives no value the record holds none: a camera without a known source cites nothing, a site the record gives as a borough is marked approximate rather than placed on a street, and a period is written exactly as the record states it. A script writes everything else the site uses from that one file, and the site's checks refuse a commit in which any of them differs from it. The About page says what the map does and does not claim; the line under the map says how many cameras there are, which years the records run to, and when they were last checked.

Take it away

  • cameras.csv - the record itself, served as it is. One header row, one camera per line, UTF-8, quoted only where a field needs it (RFC 4180). It is the file the maintainer edits, so a copy of it cannot differ from what the map draws.
  • cameras.geojson - the same cameras for a map tool: RFC 7946, one FeatureCollection, one Point per camera, written from the CSV by the same script that writes the map's own data. It opens in QGIS, in Datawrapper, and in anything else that reads GeoJSON.

The columns of the CSV, in the order they are written:

nameThe place, as the source names it.
typeOne of fixedcam, vancam, transportcam, facewatchcam, privatecam: a fixed police camera, a police van site, a British Transport Police station, a shop running Facewatch, a private estate's own system.
statusactive or legacy. Every van site is legacy: a van parks for a shift and drives away, so no van site claims to be active.
lat, lonDecimal degrees, six places, latitude first.
approximatetrue where the source gave a borough or a district rather than a street and the pin sits at the middle of the area; false otherwise.
lastThe last year the source records the camera, or blank.
periodsThe recorded uses, counted by the period the source gives them in - 2023-24:1, 2023-2025:3, 2026:4, or several separated by semicolons. Blank where the source names no period. A span is never split into years, because the source does not say which year each use fell in.
deploymentsHow many times a source records the spot being used: the sum of the periods where they are given, otherwise one.
source_labelThe record or report the entry rests on, named - "Met Police LFR deployment record, 2025", "The Register, 6 February 2026" - or blank where none is known.
source_urlWhere that document is, as an https address, or blank. Never a URL without a label.
noteThe entry's prose, preserved to the character.

The GeoJSON carries the same fields as each feature's properties, less lat and lon, which are the geometry - [longitude, latitude], the order GeoJSON insists on - with periods as an object ({"2023-24": 1}) and approximate as a boolean, and one field more, seed_key: the entry's identity in the record, built as name|lat|lon|type, which is what the map's database matches rows on and what to join this file to the API on. The collection carries a bbox and, as foreign members, the licence and the attribution line below.

The licence

The record is published under the Open Database License 1.0: copy it, plot it, join it, build on it, commercially or not, provided that you attribute it, share a database you build on it under the same licence, and do not lock it behind a technical restriction. The attribution to use is 

Contains data from cammap (https://forrest404.github.io/cammap/),
made available under the Open Database License (ODbL) 1.0.

The record was itself assembled from public sources, and each entry says which; reusing it does not remove the need to credit those where your own use calls for it. The code that draws the map is not licensed for reuse. Both are set out in the licence in the repository.

Reading it over the API

The map reads its cameras from a database view called cameras_public, through the REST interface every Supabase project has (PostgREST), with a key that is public by design: every visitor's browser holds it. Anyone may read the view the same way. It answers only what the map may read - the fourteen columns below, for the cameras that are on the map - and nothing about any account.

Copy this line as it stands:

curl "https://hdwdefswcnkzlvmyqybw.supabase.co/rest/v1/cameras_public?select=id,name,lat,lon,type,status" \
  -H "apikey: sb_publishable_ZC5aCGJcmfMqC3qMNJ2rxg_ogaOyE1r" \
  -H "Authorization: Bearer sb_publishable_ZC5aCGJcmfMqC3qMNJ2rxg_ogaOyE1r"

Both headers are needed, and both carry the same key. The answer is JSON, one object per camera. The columns the view has, and so the names select= takes:

idThe camera's number in the database. It is the same for everyone and survives a rename, and the map's own links carry it (#camera=42).
name, note, lat, lon, type, statusAs in the CSV. status can also be nonfunctional, a state a moderator sets from a report.
last_seenThe CSV's last.
deployments, periods, source_label, source_url, approximateAs in the CSV; periods is JSON.
seed_keyThe entry's identity in the record, as in the GeoJSON; null for a camera that came from a report rather than the record.

The view also holds cameras that are not in the CSV: reports that moderators have checked and put on the map. The line under the map says how many, separately from the record's own count, so the figures can be checked against the file.

Filters are PostgREST's: a column, an operator and a value in the query string. The van sites, with only their names and positions: 

curl "https://hdwdefswcnkzlvmyqybw.supabase.co/rest/v1/cameras_public?type=eq.vancam&select=name,lat,lon" \
  -H "apikey: sb_publishable_ZC5aCGJcmfMqC3qMNJ2rxg_ogaOyE1r" \
  -H "Authorization: Bearer sb_publishable_ZC5aCGJcmfMqC3qMNJ2rxg_ogaOyE1r"

eq, neq, gt, lt, in and the rest, order=, limit= and offset= are all as PostgREST documents them.

Paging and the count

A request answers up to a thousand rows, the project's default page, which is more than the record holds today; if it ever is not, ask for the rest with limit= and offset=, or with a Range: 0-999 header and then Range: 1000-1999. For the count without the rows, send Prefer: count=exact on a HEAD request and read the content-range header, which ends / and the total.

A fair rate

The whole record is one request of about a hundred kilobytes. Ask for it once and keep it, rather than once per question, and cache it for a few minutes if a page of yours asks on load, which is what the map does. A few requests a minute is nothing; a request a second from a script all day is what the project's free tier is not for, and for anything that heavy the CSV is the same data with no request at all.

Until the view is there

The view is not yet on the live project. It is added by a database change the maintainer runs by hand (migration 012 in the repository), and until that has been done the line above answers 404 with {"code":"PGRST205", … "message":"Could not find the table 'public.cameras_public' in the schema cache"}, which is what it answered on the day this page was written. The same request against the underlying table answers today, with the same headers and the same columns: 

curl "https://hdwdefswcnkzlvmyqybw.supabase.co/rest/v1/cameras?select=id,name,lat,lon,type,status" \
  -H "apikey: sb_publishable_ZC5aCGJcmfMqC3qMNJ2rxg_ogaOyE1r" \
  -H "Authorization: Bearer sb_publishable_ZC5aCGJcmfMqC3qMNJ2rxg_ogaOyE1r"

The map itself falls back to the table the same way. Once the migration has been run the view answers as written and the table stops answering the public key; if you build on this, build on the view.

What it does not answer

Nothing about anyone. The view carries no column that names a person - not who reported a camera, not who approved it, not when - and the key reads what the site shows and writes nothing without an account. The About page says what an account is and what the site keeps, which is a username of two random words, a password hash, the reports a person sent and their points, and nothing else.
